## Parecer

A implementação tem estrutura utilizável, dependências declaradas, recursos
incluídos e um fluxo offline funcional. Está adequada para preservar e continuar
o desenvolvimento em outra máquina. Não deve ser considerada integralmente
validada: há falsos positivos reproduzidos no verificador, perda de identidade
de mensagens ao agrupar canais e uma lacuna no fluxo padrão para sinais discretos.

O núcleo metodológico é bem organizado: levantamento do barramento, correlação,
busca de campos, calibração e verificação. A distinção entre hipótese física e
confirmação experimental, a exclusão da fonte de referência da busca e a
separação entre sweep e holds são decisões úteis. O procedimento de experimentos
guiados e os testes de integridade das capturas também são pontos positivos.

## Problemas reproduzidos

### P1 — Verificação aprova escala/offset errados e sinal invertido

Local: [verify.py](../.agents/skills/can-reverse-engineering/scripts/verify.py),
linhas 222–223, 261–273 e 299–321.

Foi produzido um CSV normalizado sintético com 1.200 amostras a 20 Hz, ID `0x123`,
campo little-endian de 16 bits iniciando no bit 11, três rampas triangulares,
valor bruto de 0 a 800 e referência física `raw * 0.125` (0 a 100).
A verificação foi executada com referência e `--lag 0`.

| DBC usado | Resultado observado |
| --- | --- |
| Escala `0.125`, offset `0` | `PASS`, slope `1.000`, viés zero |
| Escala `0.25`, offset `10` | **`PASS`**, slope `2.000`, viés médio `+60` (60% da faixa) |
| Escala `-0.125`, offset `100` | **`PASS`**, slope `-1.000` |

O helper de Spearman retorna magnitude e sinal; o verificador descarta o sinal.
A concordância absoluta gera um aviso, mas não entra na decisão. O residual
após ajuste afim também não entra no gate. Logo, `PASS` não confirma calibração
nem direção correta. A documentação admite aviso de viés sem reprovação para
referências enviesadas, mas não limita a magnitude desse desvio.

Recomendação: distinguir explicitamente identificação, autoconsistência e
calibração; exigir concordância positiva e tolerâncias explícitas para valores
físicos, com exceções declaradas quando a referência justificar. Adicionar
regressões para sinal invertido, escala/offset incorretos e transformação não linear.
Até lá, revisar o gráfico e a linha `abs. agreement`; não usar somente o exit code.

### P1 — IDs iguais de canais ou formatos diferentes são misturados

Local: [common.py](../.agents/skills/can-reverse-engineering/scripts/common.py),
função `group_by_id`, linhas 325–347.

O CSV preserva `ch` e `ext`, mas o agrupamento usa somente `df.groupby("id")`;
`ext` é retirado da primeira linha. Duas mensagens de mesmo ID e tamanho,
uma do canal 0 e outra do canal 1, produziram um único grupo com duas amostras.
Repetindo com o mesmo ID numérico em formatos standard e extended, o resultado
também foi um único grupo, marcado como standard quando a primeira linha era standard.

Isso pode contaminar a análise e gerar um DBC com identidade incorreta em logs
multicanal. O seletor `--id` não permite resolver essa colisão. Há caminhos com
a mesma suposição em `survey.py`, `decode_reference.py` e `combine_dbc.py`; a
correção deve revisar os consumidores, e não apenas mudar uma chave no helper.

Recomendação: selecionar canal/formato explicitamente ou preservar a identidade
composta em todo o fluxo. Até lá, analisar entradas previamente separadas por
canal e formato, preservando os originais.

### P2 — Busca padrão não contempla flags de 1–3 bits

Local: [bitsearch.py](../.agents/skills/can-reverse-engineering/scripts/bitsearch.py),
linha 189, e instruções da skill para estados discretos.

`--min-len` tem padrão 4. Uma captura sintética com somente o bit 3 alternando
entre 0 e 1, e referência correspondente, foi identificada como um byte inteiro
big-endian (`start_bit=7`, `length=8`, escala `0.125`). Com `--min-len 1`, a mesma
entrada produziu o campo correto: little-endian, bit 3, tamanho 1 e escala 1.

O byte inteiro reproduz essa captura porque os vizinhos estão constantes, mas
pode falhar quando outros bits mudarem. As instruções dizem que o fluxo normal
encontra flags discretas, sem indicar esse ajuste necessário.

Recomendação: configurar a busca para o tipo de sinal e testar flags vizinhas
independentes. No estado atual, passar `--min-len 1` para sinais de poucos bits.

## Estrutura da skill e documentação

- As duas skills mantidas passaram no `quick_validate.py`: nome e frontmatter
  válidos. Scripts, referências, DBCs auxiliares e assets locais estão presentes
  e versionados. Isso valida a estrutura, não a correção dos algoritmos.
- `.agents/` está claramente identificada como implementação mantida;
  `.claude/` está documentada como legado. A atribuição à CSS Electronics e a
  licença MIT estão preservadas.
- O `SKILL.md` principal tem **1.253 linhas e 12.376 palavras**. Repete boa parte
  das explicações de encoding, calibração, captura e OCR. Recomenda-se manter
  seleção do modo, invariantes e comandos essenciais no arquivo principal,
  movendo os procedimentos longos para referências por modo. A orientação de
  criação de skills foi usada como critério de organização e divulgação gradual.
- A skill funciona como parte deste checkout. O `requirements.txt` interno
  aponta para `../../../requirements.txt`, os exemplos usam caminhos sob
  `.agents/skills/`, e a combinação depende da skill irmã `combine-dbc`.
  Copiar apenas a pasta `can-reverse-engineering` não transporta essas dependências.
  Para a migração solicitada, clonar o repositório completo é o caminho documentado.
- A explicação de âncora física generaliza demais “repouso = zero” para corrente,
  potência, fluxo e torque. Essa condição depende do estado físico do sistema;
  um veículo parado pode continuar consumindo corrente ou produzindo torque.
  O código observa a referência, mas a instrução deve evitar induzir uma âncora falsa.
- Big-endian arbitrariamente empacotado, multiplexação do alvo, J1939/ISO-TP,
  importação MF4 direta e UI SocketCAN não estão implementados; essas limitações
  já são declaradas. Não são promessas de funcionalidade completa.

## Continuidade em outra máquina

Clonar o repositório inteiro, entrar na raiz e criar uma nova `.venv`:

```bash
git clone https://github.com/FelipeEckert/can-reverse-engineering-skills.git
cd can-reverse-engineering-skills
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-core.txt
```

Para captura e as suítes acima, usar `requirements-live.txt`. Para OCR, usar
`requirements-vision.txt` e instalar FFmpeg/ffprobe no sistema. `requirements.txt`
instala todos os grupos. Em Windows, usar `install.bat` ou o procedimento do README.

`.venv/`, `temp-output/`, `decoding-output/` e `TEMP/` são ignorados pelo Git.
Os dados de trabalho e resultados nessas pastas precisam de uma transferência
separada caso sejam necessários. A publicação da skill não inclui automaticamente
arquivos locais ainda não versionados. O corpus opendbc opcional também é externo.

Prioridade sugerida para a próxima etapa: corrigir o gate de verificação, preservar
identidade de canal/IDE, cobrir flags pequenas, integrar esses casos aos testes/CI
e então reduzir e reorganizar o arquivo principal da skill.
